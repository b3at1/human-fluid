# Security and cost boundaries

## Identity and authorization

Guest tokens and invite codes use cryptographic randomness; only SHA-256 hashes are stored. Guest cookies are HttpOnly/SameSite=Lax with 90-day expiry. Production requires HTTPS origin and Secure cookies or startup fails. No signing secret is required: authentication is a random opaque database session, not a JWT or signed development fallback. CSRF tokens are separately session-bound and rotate with redeemed invitations. Mutations require an allowed `Origin`, JSON content type and CSRF; cross-site Fetch Metadata is rejected independently. First guest creation requires allowed Origin/JSON but has no existing CSRF token. Production accepts only the configured origin. With a local HTTP `PUBLIC_ORIGIN`, development additionally allows the explicit localhost/127.0.0.1/IPv6-loopback variants on ports 5173, 8000 and the configured local port. Custom hosted development origins do not gain these aliases. Origin trust is never inferred from request Host/forwarding headers. Configuration normalizes a trailing slash/default port and rejects non-origin URLs. No credentialed wildcard CORS is enabled.

Every resource read/write checks ownership. Assessment feedback uses a common permission function in task, attempt, journal, discussion and export APIs. Completion releases only aggregate evaluation results; individual correctness also stays sealed until explicit release. A guessed instance/attempt ID confers no access.

Admin passwords are Argon2id hashes, created through an interactive CLI without defaults. Admin sessions are separately hashed cookies, expire after one hour and use SameSite=Strict. Owner login throttles persist independently of deletable guest profiles (ten attempts per coarse hashed source address in fifteen minutes); old throttle records are removed after a day. Use a trusted reverse proxy for TLS; do not blindly trust arbitrary forwarded headers. The MVP treats the transport peer as the source address, so a reverse proxy can group traffic into one conservative login limit.

Invites are high entropy, displayed once, stored hashed, expiring and atomically single-use. Redemption binds a grant to the current guest and rotates its token. A label is an owner note, not verified identity. Sharing an unused code delegates possession-based access. Another device requires a new invitation. Restore never creates identity, administrator status, grants, provider configuration or verified outcomes. Deletion cascades only the current principal's owned records and grants, and clears its cookies/local drafts. Unused/redeemed invite audit records remain owner records without a principal linkage after grant deletion.

## Inference

Inference is disabled by default and has no browser key/endpoint/model controls. Every explicit send rechecks owned completed attempt, assessment release, grant expiry/revocation, global enable state, idempotency and quotas. Page loads and status checks never make provider calls. After a running request completes, authorization is checked again before returning text. A disabled or revoked grant never starts a new provider call.

A serialized SQLite transaction reserves request and worst-case input/output tokens before transport, and commits first. Defaults: four requests/minute and thirty/day per grant; one hundred/day globally; no concurrent request per grant; 6,000 input and 1,500 output tokens/request; 225,000 grant and 750,000 global daily reserved tokens. Pending and outcome-unknown requests survive restarts and count against budgets. Identical principal/key/body returns the recorded result or current unresolved state without another call; altered bodies conflict. Unknown outcomes retain reservations and never automatically retry. Completed calls with trustworthy nonnegative usage within reservation may reconcile down. Failed calls conservatively retain allowances. Thread clearing removes text, not quota/idempotency records.

Local mode allows only backend-host names `localhost`, `127.0.0.1`, `host.docker.internal`, and `ollama`, and rejects a funded API key. Configure an actually local model; an operator's local service that proxies cloud inference must not be represented as free local inference. Cloud mode requires HTTPS, a server key, a model and `AI_CAP_VERIFIED=true`. The transport uses `/chat/completions`, `max_tokens`, no tools, no redirects and no ambient HTTP proxy. The UTF-8 serialized byte estimator plus bounded message overhead is a conservative bound only for the operator-verified byte-level tokenizer/chat protocol. The owner MUST verify their selected provider/model's cap and token semantics before enabling cloud mode. Unsupported semantics must remain disabled; setting the flag is an operational attestation, not automatic certification. No funded provider was verified during implementation.

Request/token limits are **not a dollar cap**. For monetary controls use a provider-enforced hard limit or extend reservation accounting with explicit, current prices. No price or hard spending-stop claim is built in. Outcome-unknown reservations require operator investigation; a fresh grant does not erase the global daily reservation. A process crash leaves a conservative reserved state.

Provider context is built only from the owned canonical problem, submitted answer, actual observations, deterministic explanation and at most six recent message pairs. Scratchpad is included only on explicit opt-in. No credentials, invitation codes, session tokens, admin data, unrelated attempts or future assessments are sent. The provider has no tools or grading/admin authority. User content is text, never executable HTML. Raw provider errors are not returned; replies containing the configured API key are rejected. No conversation or credential logging is added.

## Boundaries and operations

Mutation bodies are bounded to 1 MB while streaming, before JSON materialization. Answers, queries, notes, histories and restore rows have limits. JSON restore is strictly typed, at most 2,000 stored imported rows; browser imports are chunked to respect body limits and duplicates are ignored. JSON outcomes remain unverified even if marked correct in an edited backup. The server does not execute imported values.

Secrets, databases, caches and test screenshots are ignored by Git and the Docker build context. The container is non-root and supports only one app instance against the durable SQLite volume. Backups contain private history and identity hashes: protect them like the live database. No third-party analytics, fingerprinting, anonymous config dump, database browser or arbitrary proxy endpoint is provided. Health outputs contain only minimal status. Generic failures include a request ID, without environment or exception details.

The synthetic provider and private-answer routes live exclusively in the isolated `scripts/e2e_server.py` test entry point. They must never be used to host the application; production entry is `app.main:app`.
